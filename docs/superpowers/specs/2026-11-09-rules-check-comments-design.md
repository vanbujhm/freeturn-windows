# Правила: проверка адреса, комментарии, выключение

Дата: 2026-11-09. Часть А из трёх улучшений маршрутизации. Части Б («приложение только
через VPN») и В (DNS-прокси) описаны в своих спецификациях и опираются на модель правила
отсюда.

## 1. Цель

Человек правит список правил и хочет понимать, что получилось. Сейчас для этого нет ничего,
кроме подключения и наблюдения. Нужно:

- проверить домен или IP и увидеть, куда он пойдёт по правилам и куда идёт на самом деле;
- подписать правило, чтобы через месяц помнить, зачем оно;
- временно выключить правило, не удаляя его.

Готово, когда:

- у правила есть комментарий и переключатель, оба сохраняются в настройках;
- выключенное правило не действует в подключении и не считается пропущенным;
- проверка адреса без подключения показывает совпавшее правило и направление;
- проверка при подключении дополнительно показывает интерфейс, который Windows выбирает
  для каждого адреса, и подсвечивает расхождение с правилами;
- старые настройки читаются без миграции.

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Что показывает проверка | Правило всегда, факт маршрута при подключении |
| Сопоставление домена | Точное имя, как сейчас. Поддомены вводит часть В |
| Когда действуют изменения | При следующем подключении, как сейчас |
| Хранение | Новые поля в `model.Rule`, нулевые значения дают прежнее поведение |

## 3. Модель

```go
type Rule struct {
	Kind    RuleKind
	Value   string
	Comment string // до 80 символов, без управляющих
	Off     bool   // правило хранится, но не действует
}
```

`Off` выбран вместо `On`: нулевое значение в старых настройках означает «включено».

`sanitizeRules` в `cmd/freeturn/api.go`:

- обрезает пробелы по краям комментария, убирает управляющие символы, режет до 80 рун;
- сохраняет `Off`;
- повторы ищет по нормализованному значению, как сейчас; при повторе остаётся первое правило
  с его комментарием и `Off`.

`split.Compile` пропускает правила с `Off` до классификации. В `Skipped` они не попадают:
это выбор человека, а не ошибка, предупреждения о них нет.

Служба проверяет правила сама (граница доверия): та же очистка выполняется в `prepare`
через `split.Compile`, комментарий службе не нужен и в журнал не пишется.

## 4. Экран правил

Карточка правила:

- переключатель включения слева;
- значение моноширинным шрифтом и вид правила под ним;
- комментарий приглушённым текстом, если он есть;
- кнопка «Комментарий» переводит строку комментария в поле ввода: Enter сохраняет,
  Esc отменяет, пустое значение удаляет комментарий;
- кнопка «Удалить», как сейчас.

Выключенная карточка тусклая (класс `dim`, уже есть в стилях).

Строка добавления получает второе необязательное поле «Комментарий». Enter в любом из полей
добавляет правило.

Сохранение идёт через существующий `save`: окно записывает настройки и перечитывает их.
Пока запись идёт, переключатели и кнопки недоступны, как у переключателя режима. Подсказка
«подействует при следующем подключении» показывается, как сейчас.

## 5. Проверка адреса

Карточка «Проверить адрес» над списком: поле ввода и кнопка «Проверить». Ответ выводится
под полем в два блока.

### 5.1. По правилам

Чистая функция в пакете `split`:

```go
type Verdict string // "tunnel" | "direct"

type Match struct {
	Rule    model.Rule // нулевое значение: ни одно правило не совпало
	Addr    netip.Addr // для совпадения по адресу домена, иначе пусто
}

type Explanation struct {
	Input    model.Rule  // нормализованный ввод (ip, subnet или domain)
	Verdict  Verdict
	Match    Match       // действующее правило
	OffMatch Match       // выключенное правило, которое совпало бы
	SplitOff bool        // раздельное туннелирование выключено, всё через туннель
}

func Explain(o model.Options, input string, addrs []netip.Addr) (Explanation, error)
```

Порядок:

1. Ввод нормализуется через `Classify`. Неверный ввод даёт `ErrInvalid`, маска даёт
   `ErrWildcard`, как при добавлении. Ввод подсети отклоняется: проверяется адрес или домен.
2. Если `SplitOff`, ответ «через туннель», правила не смотрятся.
3. Для домена ищется доменное правило с тем же именем.
4. Для IP и для каждого адреса из `addrs` ищется правило IP или подсеть, содержащая адрес.
   Из нескольких подсетей выбирается самая узкая. Правило IP узже любой подсети.
5. Действующее совпадение даёт направление по режиму: в режиме «список напрямую» это
   `direct`, в режиме «через VPN только список» это `tunnel`. Нет совпадения: наоборот.
6. Совпадение с выключенным правилом ищется так же по правилам с `Off` и попадает в
   `OffMatch`, если действующего совпадения нет.

Окно вызывает `Explain` через новый метод `API.ExplainRule(value)`. Без подключения `addrs`
пуст, поэтому домен сопоставляется только по имени.

### 5.2. Сейчас

Только когда фаза `connected` или `reconnecting`. Окно шлёт службе новую команду IPC
`probe` с вводом. Служба:

1. для домена разрешает его на той стороне, куда пойдёт его трафик, срок 3 секунды:
   - имя под правилом обхода (режим «список напрямую») и имя не из списка в режиме «через
     VPN только список» спрашиваются тем же `Resolver`, что и правила: DNS физического
     интерфейса по защищённым сокетам;
   - остальные имена, и все при выключенном раздельном туннелировании, спрашиваются у DNS
     конфига по сокетам, привязанным к адаптеру туннеля (`IP_UNICAST_IF`). Так имя, которое
     человек собирается открыть через VPN, не уходит провайдеру открытым текстом, а адреса
     совпадают с теми, что получит браузер;
   - если в конфиге нет DNS, система и так спрашивает физический, и проверка тоже;
2. для каждого адреса вызывает `GetBestRoute2` и сравнивает интерфейс маршрута с LUID
   адаптера туннеля и физического интерфейса сессии;
3. отвечает списком `{Addr, Via}`, где `Via` это `tunnel`, `direct` или `other`.

Команда только читает: маршрутов и правил брандмауэра она не меняет. Без сессии служба
отвечает ошибкой `not_connected`, окно тогда показывает только блок «По правилам».

Окно передаёт полученные адреса в `Explain` и выводит построчно: адрес, направление по
правилам, факт. Строка с расхождением подсвечивается и получает пояснение:

- правила менялись после подключения: окно запоминает `Options` последнего запроса
  `Connect` и, если `Explain` по ним даёт другое направление, пишет «правила изменены,
  подействуют при переподключении»;
- домен совпал с правилом, а адреса ещё нет среди маршрутов: «новый адрес домена,
  маршрут появится при следующем обновлении доменов»;
- иначе: «маршрут другой программы» без догадок.

Если домен не разрешился, блок «Сейчас» так и пишет и показывает только «По правилам».

## 6. Ошибки

- Неверный ввод: тост с текстом из `split`, как при добавлении правила.
- Служба недоступна или не подключена: блок «Сейчас» скрыт, остаётся «По правилам».
- `GetBestRoute2` вернул ошибку для адреса: в строке «не удалось узнать маршрут».

## 7. Тесты

- `split`: табличные тесты `Explain`. Оба режима, `SplitOff`, выключенное правило,
  самая узкая подсеть, правило IP против подсети, IPv6, адреса домена против подсети,
  неверный ввод, маска, подсеть на входе.
- `split.Compile`: правила с `Off` не попадают ни в результат, ни в `Skipped`.
- `cmd/freeturn`: `sanitizeRules` с комментариями (обрезка, управляющие символы, 80 рун,
  повтор сохраняет первый комментарий), круговой JSON старых настроек без новых полей.
- `internal/ipc`: круговой тест сообщения `probe` и ответа.
- `internal/engine`: `probe` без сессии даёт `not_connected`, с сессией собирает ответ из
  поддельных `Resolver` и маршрутизатора.
- `internal/netcfg`: админ-тест `GetBestRoute2` для адреса loopback и адреса шлюза.
- Фронтенд (`rules.test.ts`): переключатель выключает правило и сохраняет настройки,
  редактирование комментария (Enter, Esc, пусто), вывод проверки с расхождением и без
  блока «Сейчас».
