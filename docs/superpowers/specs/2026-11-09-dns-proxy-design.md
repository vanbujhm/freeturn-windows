# DNS-прокси: поддомены и журнал запросов

Дата: 2026-11-09. Часть В из трёх улучшений маршрутизации. Опирается на
`2026-11-09-rules-check-comments-design.md` (модель правила и проверка адреса).

## 1. Цель

Сейчас доменное правило действует только для точного имени: служба заранее разрешает имена
из списка и ставит маршруты на их адреса. Поддомены перечислить нельзя, а что на самом деле
спрашивают программы, не видно.

Служба становится DNS-сервером системы на время сеанса. Каждый ответ она видит до того, как
его получит программа, и успевает поставить маршрут.

Готово, когда:

- правило `example.com` действует для `example.com` и любого его поддомена;
- первое соединение к новому поддомену идёт по маршруту правила, а не мимо него;
- имя под правилом разрешается DNS-сервером той стороны, куда пойдёт его трафик;
- вкладка «Запросы» показывает имена, адреса, направление и сработавшее правило;
- журнал запросов не попадает на диск и в диагностику;
- если прокси не запустился, подключение работает по прежней схеме.

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Смысл доменного правила | Имя и все поддомены. Смысл старых правил меняется, это в заметках к версии |
| Адрес прокси | `127.0.0.53:53`, UDP и TCP |
| Как система попадает в прокси | Правило NRPT для `.` и DNS адаптера туннеля |
| Выбор DNS-сервера | Имя разрешается там же, куда пойдёт его трафик |
| Порядок | Ответ программе уходит после маршрута, ожидание до 1,5 с |
| Кеш | Нет, кеширует Dnscache |
| Журнал | Отдельная вкладка, кольцевой буфер в памяти службы, 2000 записей |

## 3. Сопоставление

`split.Match(rules, name)` возвращает доменное правило, если `name == rule` или `name`
кончается на `"." + rule`. Имена сравниваются в ASCII-виде (punycode) без точки на конце и
в нижнем регистре, как хранятся правила. Из нескольких совпадений выбирается самое длинное
правило.

`split.Explain` из части А переходит на `Match`, поэтому проверка адреса понимает поддомены.

Заранее разрешаемые при подключении имена правил и их периодическое обновление
(`refreshDomains`) остаются: апекс домена получает маршрут сразу, и всё работает, если
прокси не запустился.

## 4. Пакет `internal/dnsproxy`

### 4.1. Приём

Прокси слушает `127.0.0.53:53` по UDP и TCP с `SO_EXCLUSIVEADDRUSE`. Запросы разбираются
через `golang.org/x/net/dns/dnsmessage`, новых зависимостей нет. Запрос с несколькими
вопросами или без вопроса получает `FORMERR`. Запрос уходит серверу тем же транспортом,
каким пришёл, и ответ сервера отдаётся программе как есть, с флагом TC, если сервер его
поставил: тогда программа сама повторит по TCP.

### 4.2. Выбор DNS-сервера

| Режим | Имя под правилом | Остальные имена |
| --- | --- | --- |
| Список напрямую | DNS физического интерфейса | DNS конфига через туннель |
| Через VPN только список | DNS конфига через туннель | DNS физического интерфейса |

Если в конфиге нет DNS, вместо DNS туннеля берётся DNS физического интерфейса. Если
раздельное туннелирование выключено, все имена идут на DNS конфига через туннель.

Сокеты к DNS физического интерфейса защищаются `protect`, как сейчас в `split.DNSResolver`.
Сокеты к DNS туннеля привязываются к адаптеру туннеля через `IP_UNICAST_IF` с индексом
адаптера: так им не нужны маршруты, и в режиме «только список» DNS конфига доступен без
маршрута на него.

Серверы опрашиваются по очереди, срок 3 секунды на запрос делится между ними, как в
`DNSResolver.lookup`. Ответ сервера с `NXDOMAIN` окончателен. Все серверы молчат или
ошибаются: программа получает `SERVFAIL`.

Запросы любых типов пересылаются по тому же выбору. Адреса смотрятся только в ответах
A и AAAA.

### 4.3. Применение адресов

Для имени под правилом прокси собирает адреса A и AAAA из ответа, отбрасывает
непригодные (`unroutable` из `split`) и вызывает обработчик движка:

```go
type Sink interface {
	// Apply ставит разрешения и маршруты для адресов имени под правилом.
	// Возвращается, когда всё применено или ctx истёк.
	Apply(ctx context.Context, addrs []netip.Addr) error
}
```

Ответ программе уходит после возврата `Apply`. Срок ожидания 1,5 секунды. По истечении или
при ошибке ответ всё равно уходит, а в журнале службы появляется строка. Тогда соединение
в режиме «список напрямую» пойдёт через туннель, в режиме «только список» напрямую, пока
следующая сверка не поставит маршрут.

Движок реализует `Apply` так:

1. новые адреса добавляются в `s.resolved` (`addResolved`);
2. если новых нет, возврат сразу;
3. иначе вызов существующего `applyAddresses`: сначала блокировка, потом маршруты.

Одновременные вызовы склеиваются: пока идёт применение, следующие адреса копятся, и после
окончания идёт одно общее применение. Каждый ждущий `Apply` возвращается после того
применения, в которое попали его адреса. Так сессия WFP не пересоздаётся на каждый ответ.

Предел динамических адресов 4096 за сеанс сверх адресов, разрешённых заранее. Сверх
предела `Apply` возвращает ошибку без применения, предупреждение `WarnDNSLimit` выводится
один раз за сеанс.

### 4.4. Направление системы в прокси

1. **NRPT.** Служба пишет ключ
   `HKLM\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters\DnsPolicyConfig\{FreeTurn-<guid>}`
   с `Name = "."`, `GenericDNSServers = "127.0.0.53"`, `ConfigOptions = 8` и `Version = 2`.
   Это не даёт Windows параллельно спрашивать DNS физической сети.
2. **DNS адаптера.** Если прокси запущен, `ApplyTunnelRoutes` и путь режима «только список»
   ставят адаптеру туннеля DNS `127.0.0.53` вместо DNS конфига. Если не запущен, всё как
   сейчас. DNS конфига уходит прокси как сервер
   стороны туннеля.
3. **Kill switch.** В запрет DNS (`blockDNS`) к исключениям добавляется `127.0.0.53`:
   разрешение loopback (вес 13) ниже запрета DNS (14). Запросы прокси к серверам идут от
   службы и разрешены её правилом (15).

Ключ NRPT записывается в `statefile` рядом с маршрутами обхода. При отключении служба
снимает ключ и сбрасывает кеш Dnscache. Следующий запуск службы после падения снимает ключ
из `statefile`. Удаление программы снимает ключи с префиксом `FreeTurn-`.

**Проба до реализации.** Первой задачей плана проверяется на машине автора: применяет ли
Dnscache ключ сразу после записи, и какой вызов для этого нужен (сброс кеша, перечитывание
политики, ничего). Если применить без перезапуска Dnscache нельзя, NRPT убирается из
дизайна, остаётся DNS адаптера, а ограничение про параллельные запросы к DNS физической
сети уходит в подсказку. Об этом решении автор узнаёт до продолжения работы.

### 4.5. Время жизни

Прокси запускается на шаге 5 до установки DNS адаптера и NRPT, останавливается при откате
сессии после снятия NRPT и DNS адаптера. Смена физической сети обновляет у прокси DNS
физического интерфейса и индекс адаптера, ничего не перезапуская.

## 5. Журнал запросов

### 5.1. Служба

Кольцевой буфер на 2000 записей в памяти службы:

```go
type QueryEntry struct {
	Seq      uint64
	Time     time.Time
	Name     string
	Type     string        // A, AAAA, HTTPS, ...
	Addrs    []netip.Addr  // до 8
	Upstream string        // tunnel | direct
	Route    string        // tunnel | direct: куда пойдёт трафик адресов
	Rule     string        // значение сработавшего правила или пусто
	RCode    string
	Took     time.Duration
	Late     bool          // ответ ушёл до применения маршрута
}
```

Команды IPC:

- `queries` с `since`: записи с `Seq > since` и последний `Seq`;
- `queries_clear`: очистить буфер.

Записи переживают переподключение и стираются при перезапуске службы и по `queries_clear`.
На диск не пишутся, в «Сохранить диагностику» не попадают, в журнал службы имена не идут.

### 5.2. Вкладка «Запросы»

- Новая вкладка между «Маршрутизацией» и «Журналом».
- Пока вкладка открыта, окно раз в секунду спрашивает `queries` с последним `Seq`.
- Таблица: время, имя, адреса (свёрнуты, если больше двух), метка «VPN» или «напрямую»,
  правило, метка «поздно» для `Late`.
- Фильтр по подстроке имени и переключатель «только с правилом».
- У строки кнопка «Добавить правило»: открывает экран правил с именем в поле ввода, человек
  может его поправить перед добавлением.
- Кнопка «Очистить».
- Без подключения или без прокси: пояснение, почему пусто.

## 6. Тексты

- Подсказка экрана правил: домен действует и для поддоменов.
- Предупреждение там же, когда есть доменные правила: безопасный DNS (DoH) в браузере идёт
  мимо FreeTurn, и доменные правила для браузера тогда не действуют.
- Заметки к версии: смысл старых доменных правил расширился до поддоменов.

## 7. Ошибки

| Сбой | Поведение |
| --- | --- |
| Порт 53 на `127.0.0.53` занят | Прокси не запущен, прежняя схема, `WarnDNSProxy` |
| Ошибка записи NRPT | Только DNS адаптера, `WarnDNSProxy` с причиной |
| Серверы не ответили | `SERVFAIL` программе |
| `Apply` не успел или упал | Ответ уходит, строка в журнале, `Late` в записи |
| Предел адресов | `WarnDNSLimit` один раз, маршруты не ставятся |

## 8. Тесты

- `split.Match`: апекс, поддомен, похожий суффикс без точки (`badexample.com`), самое
  длинное правило, регистр, точка на конце, punycode.
- `dnsproxy` с поддельными DNS-серверами на свободных портах (как `resolve_test.go`):
  - таблица выбора сервера по режиму, правилу и наличию DNS конфига;
  - ответ уходит только после возврата `Apply`;
  - ответ уходит по истечении 1,5 с с `Late`;
  - склейка одновременных `Apply`;
  - предел адресов;
  - TCP, TC-урезание, `FORMERR`, `SERVFAIL`, `NXDOMAIN` без опроса следующего сервера.
- Буфер запросов: переполнение, `since`, очистка.
- `engine`: прокси запускается и останавливается в нужном порядке с откатом, отказ привязки
  даёт прежнюю схему с предупреждением, смена сети обновляет серверы.
- `statefile`: ключ NRPT сохраняется и снимается следующим запуском после падения.
- Админ-тест: записать NRPT, `Resolve-DnsName` приходит в прокси, снять ключ, запросы
  снова идут мимо.
- Фронтенд: вкладка «Запросы» (опрос, фильтр, «только с правилом», «Добавить правило»
  переносит имя на экран правил, очистка).
